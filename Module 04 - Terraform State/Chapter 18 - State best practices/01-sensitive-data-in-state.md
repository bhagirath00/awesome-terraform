# Sensitive Data in State

## Introduction

One of the most important things to understand about Terraform state is that it stores sensitive data in plain text. Passwords, private keys, API tokens, connection strings, and other secrets that flow through Terraform resources end up in the state file — readable by anyone who can access it.

This is not a bug — it is a fundamental requirement of how Terraform works. Terraform needs to store complete resource attribute values in state so it can detect changes, calculate diffs, and manage resource lifecycles. But it means you must treat your state file with the same care as any other secret.

---

## What Sensitive Data Ends Up in State

### Database Passwords

```hcl
resource "aws_db_instance" "app" {
  identifier = "myapp-db"
  engine     = "mysql"
  username   = "admin"
  password   = var.db_password   # This value ends up in state in plain text
}
```

After apply, the state contains:

```json
"attributes": {
  "username": "admin",
  "password": "SuperSecret123!",   ← plain text in state
  ...
}
```

---

### IAM Access Keys

```hcl
resource "aws_iam_access_key" "deploy_user" {
  user = aws_iam_user.deploy.name
}

output "access_key_secret" {
  value     = aws_iam_access_key.deploy_user.secret
  sensitive = true
}
```

The access key ID and secret are both stored in state:

```json
"attributes": {
  "id": "AKIAIOSFODNN7EXAMPLE",
  "secret": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY",   ← plain text
  ...
}
```

---

### TLS Private Keys

```hcl
resource "tls_private_key" "server" {
  algorithm = "RSA"
  rsa_bits  = 4096
}

resource "aws_key_pair" "server" {
  key_name   = "server-key"
  public_key = tls_private_key.server.public_key_openssh
}
```

The private key is stored in state:

```json
"attributes": {
  "private_key_pem": "-----BEGIN RSA PRIVATE KEY-----\nMIIEo...",   ← plain text
  "public_key_openssh": "ssh-rsa AAAA...",
  ...
}
```

---

### Random Passwords Generated by Terraform

```hcl
resource "random_password" "db" {
  length  = 24
  special = true
}

resource "aws_db_instance" "app" {
  password = random_password.db.result
}
```

The generated password is in state:

```json
"attributes": {
  "result": "K#8mPx@2qR!nL5vB$9wE3jY7",   ← plain text
  ...
}
```

---

### Other Common Sensitive Values in State

- Kubernetes cluster credentials (client certificates, tokens)
- Docker registry passwords
- SMTP credentials
- Vault tokens
- SSH private keys
- JWT signing secrets
- Any value marked `sensitive = true` in a variable or output

---

## The `sensitive` Flag Does Not Protect State

A common misconception: many engineers think marking a variable as `sensitive = true` protects it in the state file. It does not.

The `sensitive` flag only hides the value from:
- Terminal output during `terraform plan`
- Terminal output during `terraform apply`
- Terraform log files

It does NOT hide the value from:
- The state file (stored in plain text)
- `terraform state show` output
- `terraform state pull` output
- Anyone with read access to the state file

```hcl
variable "db_password" {
  type      = string
  sensitive = true   # hides from plan/apply output ONLY
}
```

The state file still contains the plain text password.

## How to Protect Sensitive Data in State

### Protection 1: Encrypt the State File (Always Do This)

For S3 backend, always enable server-side encryption:

```hcl
terraform {
  backend "s3" {
    bucket  = "mycompany-terraform-state"
    key     = "production/terraform.tfstate"
    region  = "us-east-1"
    encrypt = true   # enables AES-256 encryption at rest
  }
}
```

For higher security, use AWS KMS with customer-managed keys:

```hcl
terraform {
  backend "s3" {
    bucket         = "mycompany-terraform-state"
    key            = "production/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    kms_key_id     = "arn:aws:kms:us-east-1:123456789:key/your-key-id"
  }
}
```

With KMS:
- The state file is encrypted with your own key
- Access to the state requires both S3 permissions AND KMS decrypt permission
- Key usage is logged in CloudTrail
- You can revoke access by disabling the key

---

### Protection 2: Restrict IAM Access to the State Bucket

Not everyone needs to read the state file. Apply least-privilege access:

```hcl
# IAM policy: read-only access to state (for planning)
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:ListBucket"],
  "Resource": [
    "arn:aws:s3:::mycompany-terraform-state",
    "arn:aws:s3:::mycompany-terraform-state/production/*"
  ]
}

# IAM policy: full access to state (for applying)
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
  "Resource": [
    "arn:aws:s3:::mycompany-terraform-state",
    "arn:aws:s3:::mycompany-terraform-state/production/*"
  ]
}
```

Only CI/CD pipelines and senior engineers should have write access to production state.

---

### Protection 3: Never Commit State to Git

Add state files to `.gitignore` immediately:

```gitignore
# .gitignore
*.tfstate
*.tfstate.backup
.terraform/
crash.log
*.tfvars  # if tfvars contain secrets
```

If state is ever committed to Git by accident, treat all secrets in that state as compromised. Rotate every secret immediately.

---

### Protection 4: Use AWS Secrets Manager Instead of Direct Values

Instead of passing secrets directly to resources (which stores them in state), use AWS Secrets Manager and reference the secret ARN:

```hcl
# LESS IDEAL — password stored in state
resource "aws_db_instance" "app" {
  password = var.db_password   # ends up in state
}

# BETTER — use Secrets Manager
resource "aws_secretsmanager_secret" "db_password" {
  name = "/myapp/production/db-password"
}

resource "aws_secretsmanager_secret_version" "db_password" {
  secret_id     = aws_secretsmanager_secret.db_password.id
  secret_string = var.db_password
}

# Application fetches the password at runtime from Secrets Manager
# Terraform state contains the secret ARN, not the password itself
resource "aws_db_instance" "app" {
  manage_master_user_password = true   # AWS manages rotation, password not in state
}
```

When using `manage_master_user_password = true`, AWS manages the password through Secrets Manager and the password itself is never stored in Terraform state.

---

### Protection 5: Use Random Passwords with Secrets Manager

Generate passwords with Terraform but store them in Secrets Manager — keeping the actual password out of your code while still keeping it manageable:

```hcl
resource "random_password" "db" {
  length           = 24
  special          = true
  override_special = "!#$%^&*"
}

resource "aws_secretsmanager_secret" "db_password" {
  name                    = "/myapp/production/db-password"
  recovery_window_in_days = 7
}

resource "aws_secretsmanager_secret_version" "db_password" {
  secret_id     = aws_secretsmanager_secret.db_password.id
  secret_string = random_password.db.result
}

resource "aws_db_instance" "app" {
  username = "admin"
  password = random_password.db.result   # still ends up in state
}
```

Note: The random password still ends up in Terraform state. The Secrets Manager copy provides easier rotation and access control, but the state file concern remains.

---

### Protection 6: Vault Provider for Dynamic Credentials

For the highest security, use HashiCorp Vault to generate dynamic, short-lived credentials:

```hcl
provider "vault" {
  address = "https://vault.mycompany.com"
}

data "vault_aws_access_credentials" "creds" {
  backend = "aws"
  role    = "terraform-role"
}

provider "aws" {
  access_key = data.vault_aws_access_credentials.creds.access_key
  secret_key = data.vault_aws_access_credentials.creds.secret_key
}
```

Dynamic credentials expire after use, significantly reducing the risk of state file exposure.

## Detecting and Auditing Sensitive Data in State

### Check What's in Your State

Before sharing state or granting access, audit what sensitive data it contains:

```bash
# Pull state and search for potential secrets
terraform state pull | jq -r '
  .resources[].instances[].attributes
  | to_entries[]
  | select(.key | test("password|secret|key|token|credential"; "i"))
  | "\(.key): \(.value)"
'
```

---

### CloudTrail Monitoring

With CloudTrail enabled, every access to the state file is logged:

```bash
# Find who accessed the state file in the last 24 hours
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=ResourceName,AttributeValue=mycompany-terraform-state \
  --start-time $(date -d '24 hours ago' --iso-8601=seconds) \
  --region us-east-1
```

Set up alerts for unexpected access:

```hcl
resource "aws_cloudwatch_metric_alarm" "state_access" {
  alarm_name          = "terraform-state-access"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = "1"
  metric_name         = "NumberOfObjectsGetRequests"
  namespace           = "AWS/S3"
  period              = "300"
  statistic           = "Sum"
  threshold           = "0"
  alarm_description   = "Someone accessed the Terraform state file"
}
```

## What To Do If State is Exposed

If your state file is accidentally exposed (committed to Git, shared publicly, etc.):

**Step 1: Rotate ALL secrets immediately**

Assume every secret in the state file is compromised:
- Rotate all database passwords
- Delete and recreate all IAM access keys
- Revoke and regenerate all API keys and tokens
- Regenerate TLS certificates and private keys

**Step 2: Remove the state from Git history**

If committed to Git:
```bash
# Remove the file from all history
git filter-branch --force --index-filter \
  'git rm --cached --ignore-unmatch terraform.tfstate' \
  --prune-empty --tag-name-filter cat -- --all

# Force push (this rewrites history — coordinate with team)
git push origin --force --all
```

**Step 3: Enable encryption immediately**

If state was not encrypted, enable it now and migrate the state file.

**Step 4: Review audit logs**

Check who accessed the exposed state and when. Report to security team if required.

---

## Summary

- Terraform state stores sensitive data in plain text — passwords, keys, tokens, certificates
- Common sources: `aws_db_instance` password, `aws_iam_access_key` secret, `tls_private_key`, `random_password`
- The `sensitive` flag only hides values from plan/apply output — it does NOT protect state
- Always encrypt state at rest using S3 server-side encryption or KMS
- Restrict IAM access to the state bucket — only CI/CD and authorized engineers should have access
- Never commit state files to Git — add them to `.gitignore` immediately
- Use AWS Secrets Manager or `manage_master_user_password` to keep passwords out of state where possible
- Audit state access using CloudTrail and set up alerts for unexpected access
- If state is exposed: rotate all secrets immediately, remove from Git history, enable encryption
