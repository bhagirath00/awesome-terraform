# Mastering the CLI: Terraform Workspace Commands

The efficiency of a multi-environment Terraform workflow depends on the engineer's ability to navigate and manage workspaces via the Command Line Interface (CLI). Terraform provides a dedicated sub-command, `terraform workspace`, with several actions to manage the lifecycle of these isolated state environments. This chapter provides a technical breakdown of each command, its operational impact, and best practices for automation.

## 1. List Workspaces: `terraform workspace list`

The `list` command displays all available workspaces for the current configuration.

```bash
$ terraform workspace list
  default
* dev
  prod
  staging
```

### 1.1 Understanding the Output
- **The Asterisk (`*`):** Indicates the currently "Selected" workspace. Any `plan`, `apply`, or `destroy` command you run will apply to this workspace only.
- **State Source:** The list is generated by querying the current backend. If you are using a remote backend (like S3), Terraform will query the remote storage to find all prefixes or keys associated with different workspaces.

## 2. Create a New Workspace: `terraform workspace new`

To create a new isolation layer, use the `new` command followed by the desired name.

```bash
$ terraform workspace new feature-testing
Created and switched to workspace "feature-testing"!
```

### 2.1 Technical Side Effects
- **State Initialization:** Terraform creates a new, empty state file. It does **not** copy the state from the previous workspace.
- **Immediate Selection:** By default, creating a new workspace automatically "selects" it as the active context.
- **Directory Creation:** If using a local backend, a new subdirectory is created under `terraform.tfstate.d/`.

## 2. Switch Workspaces: `terraform workspace select`

The `select` command changes the active workspace. This is the most frequent command used in developer workflows.

```bash
$ terraform workspace select prod
Switched to workspace "prod".
```

### 2.1 Operational Precautions
- **State Refresh:** When you switch workspaces, the next time you run `terraform plan`, Terraform will perform a full refresh against the state file associated with the *new* workspace.
- **Context Awareness:** It is very easy to forget which workspace is active. Always run `terraform workspace show` before executing destructive commands.

## 3. Identify Active Workspace: `terraform workspace show`

This command simply prints the name of the currently selected workspace. 

```bash
$ terraform workspace show
dev
```

### 3.1 Use in Automation and CI/CD
In a Jenkins, GitHub Actions, or GitLab CI pipeline, you can use this command to ensure the pipeline is operating on the correct environment.
```bash
if [ "$(terraform workspace show)" != "$TARGET_ENV" ]; then
  echo "Error: High-risk workspace mismatch detected!"
  exit 1
fi
```

## 4. Delete a Workspace: `terraform workspace delete`

To remove a workspace and its associated state file, use the `delete` command.

```bash
$ terraform workspace delete feature-testing
Removed workspace "feature-testing"!
```

### 4.1 Safety Constraints
- **Active Workspace:** You cannot delete the workspace that is currently selected. You must first switch to another workspace.
- **Empty State Check:** Terraform will refuse to delete a workspace if its state file contains managed resources. This is a critical safety feature to prevent accidental deletion of infrastructure.
- **The `-force` Flag:** If you truly want to delete a workspace that still has resources (e.g., if you've already manually deleted the resources in the cloud console), you can use the `-force` flag. Use this with extreme caution.

## 5. Scripting a Multi-Environment Workflow

A typical automated deployment script for a new feature branch might look like this:

```bash
# Ensure we are initialized
terraform init

# Create or switch to the branch-specific workspace
terraform workspace select $BRANCH_NAME || terraform workspace new $BRANCH_NAME

# Apply the infrastructure
terraform apply -auto-approve

# ... run tests ...

# Switch back and cleanup
terraform workspace select default
terraform workspace delete -force $BRANCH_NAME
```

## 6. Common Issues and Troubleshooting

### 6.1 State Locking
Workspaces use the same backend locking mechanism as standard Terraform operations. If a colleague is running an `apply` in the `prod` workspace, you will be unable to switch to or modify that workspace until their lock is released.

### 6.2 Backend Transitioning
If you change your `backend` block (e.g., moving from local to S3), Terraform will offer to migrate your state. Be aware that it will attempt to migrate the state for **all** workspaces it finds in the `terraform.tfstate.d` directory.

### 6.3 Missing Workspaces
If you run `list` and don't see your expected workspaces after changing machines, ensure that you have run `terraform init`. Workspaces in remote backends are only discovered during the initialization process when the backend plugin is configured.

## 7. Summary

The `terraform workspace` CLI is the command center for multi-environment orchestration. By mastering the six primary actions—`list`, `new`, `select`, `show`, `delete`, and `init`—you can manage complex staging and production pipelines with high precision. Understanding the technical behavior of these commands—especially regarding state isolation and safety checks—is fundamental to building a reliable, automated DevOps lifecycle.
