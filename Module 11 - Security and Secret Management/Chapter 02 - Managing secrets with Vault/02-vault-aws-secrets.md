# Temporary Access: Vault's AWS Secret Engine

One of the most powerful features of HashiCorp Vault is its ability to generate short-lived, dynamic credentials for cloud providers. Instead of storing permanent AWS Access Keys in your Terraform repository or environment variables, you can use the Vault AWS Secret Engine to generate new, unique credentials for every `apply` cycle. These credentials automatically expire when their time-to-live (TTL) is reached, virtually eliminating the risk of long-term credential leakage. This chapter provide a definitive deep dive into the technical configuration of the `vault_aws_secret_backend` and the workflow for consuming dynamic IAM credentials in your Terraform modules.

## 1. Technical Mechanics: Dynamic Identity

The AWS Secret Engine in Vault works by interacting with the AWS IAM API on your behalf.

1.  **Backend Config:** You provide Vault with an IAM user that has permissions to create other users and roles.
2.  **Role Definition:** You define a "Role" in Vault that maps to a set of IAM permissions (e.g., `AdministratorAccess` or a custom JSON policy).
3.  **Generation:** When a user or pipeline requests credentials from that role, Vault creates a temporary IAM user or assumes a role, generates access keys, and returns them to the requester.
4.  **Revocation:** When the TTL expires, Vault automatically deletes the IAM user or revokes the session.

## 2. Configuring the Backend with Terraform

Using the "Vault as Code" pattern, you can manage this entire security pipeline.

```hcl
# 1. Enable the AWS secret engine
resource "vault_aws_secret_backend" "aws" {
  access_key = var.master_aws_key
  secret_key = var.master_aws_secret
  region     = "us-east-1"
}

# 2. Define a role with specific IAM permissions
resource "vault_aws_secret_backend_role" "deploy_role" {
  backend         = vault_aws_secret_backend.aws.path
  name            = "terraform-deployer"
  credential_type = "iam_user"

  policy_document = <<EOT
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ec2:*",
      "Resource": "*"
    }
  ]
}
EOT
}
```

## 3. Consuming Dynamic Credentials in Terraform

To use these temporary keys for your main AWS provider, you use a data source.

```hcl
data "vault_aws_access_credentials" "creds" {
  backend = vault_aws_secret_backend.aws.path
  role    = vault_aws_secret_backend_role.deploy_role.name
}

provider "aws" {
  region     = "us-east-1"
  access_key = data.vault_aws_access_credentials.creds.access_key
  secret_key = data.vault_aws_access_credentials.creds.secret_key
}
```

## 4. The Power of TTL (Time To Live)

Security is often a race against time. 
- **The Protection:** If an attacker steals the access keys generated by Vault, they only have a limited window of opportunity (typically 15-60 minutes) before the keys are automatically neutralized by Vault.
- **Configuring TTL:** You can set the `default_lease_ttl` and `max_lease_ttl` on the backend to match your organization's risk tolerance.

## 5. Summary

The Vault AWS Secret Engine is the pinnacle of "Least Privilege" identity management. By moving away from static keys and toward dynamic, session-based credentials generated on-demand, you create an infrastructure that is both highly secure and fully automated. Terraform's ability to orchestrate the backend configuration and then consume the resulting credentials provides a seamless, "Zero-Trust" experience for managing cloud foundations at scale. Mastering these dynamic identity patterns is a mandatory requirement for any senior DevOps professional working in high-compliance or highly sensitive enterprise environments.
